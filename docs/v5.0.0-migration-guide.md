# Migration guide: v4.x → v5.0.0

v5.0.0 graduates the JSON report contract to **`reports/1.0`** and introduces the **Evidence Model v2** plus optional **SARIF 2.1.0** output. The wire-stability guarantees of `1.x` are described in `docs/reports-contract-v1.0.md`.

This page lists every public surface that changes and what to do about it.

## At a glance

| Change | Effect on existing users |
|---|---|
| Default report contract → `reports/1.0`. | New default. `--report-json-contract 0.3` keeps the v4 shape. |
| `reports/0.1` removed from CLI selector. | `--report-json-contract 0.1` returns a usage error with migration text. |
| Legacy profile id `github-release-hardening` removed. | `--profile github-release-hardening` returns exit `2` with migration text. Use `github-release-hardening-1`. |
| Per-result `evidence` object (Evidence Model v2). | Only present in `reports/1.0`. `0.3`/`0.2` payloads are unchanged. |
| `--sarif-output PATH` flag. | Additive. SARIF is only written when the flag is set. |
| `confidence` enum normalization (`high|medium|low|none`). | Free-form values are mapped on emission for `1.0`. `0.3` keeps the original string. |
| Bundled v3 schema is now UTF-8 (was UTF-16 with BOM). | Hygiene. Validators that assumed UTF-8 should now succeed. |

## Choosing your migration path

### Path A — keep using `reports/0.3`

If your downstream tooling parses the v4 JSON shape directly, pin the contract:

```bash
python -m oss_policy_kit evaluate --target . --profile github-level-1 \
  --output-dir ./out --report-json-contract 0.3
```

Behavior is byte-for-byte equivalent to v4.0.4. No v1 keys appear in the payload.

### Path B — adopt `reports/1.0`

Drop the flag (or pass `--report-json-contract 1.0`). The new shape is documented in `docs/reports-contract-v1.0.md`. Update parsers to:

- read `profile.id` and `profile.title` instead of the flat `profile_id` / `profile_title`;
- read `scorecard.path` / `scorecard.supplemental` instead of the flat `scorecard_path` / `scorecard_supplemental`;
- read `results[].evidence.*` instead of `results[].evidence_sources` and `results[].evidence_collection_method`;
- normalize `results[].confidence` against the `high|medium|low|none` enum (free-form strings are now normalized on emission);
- optionally key drift comparisons off `results_digest`.

## CLI changes

### `--report-json-contract`

| Value | v4.0.4 | v5.0.0 |
|---|---|---|
| `1.0` | (n/a) | **Default.** |
| `0.3` | Default. | Selectable. |
| `0.2` | Selectable. | Selectable. |
| `0.1` | Selectable. | **Removed.** Returns an error. |

The error text for `0.1` is:

> Report JSON contract '0.1' was removed in v5.0.0. Use '1.0' (default), '0.3', or '0.2'. See docs/v5.0.0-migration-guide.md.

### Removed legacy profile alias `github-release-hardening`

The legacy bundled profile id `github-release-hardening` (without a numeric suffix) is **removed** in v5.0.0. Passing `--profile github-release-hardening` now exits with code `2` and the message:

> Profile id 'github-release-hardening' was removed in v5.0.0. The canonical profile is 'github-release-hardening-1' (same control set). Update your scripts and CI workflows. See docs/v5.0.0-migration-guide.md.

The control set is unchanged. Update CI workflows, scripts, and dashboards that still reference the bare id to use `github-release-hardening-1` (the canonical id) instead. The two ids resolved to the same control list in v4.x, so there is no behavioral change beyond the id rename.

### `--sarif-output PATH`

New flag on `evaluate`. When set, the kit also writes a SARIF 2.1.0 log:

```bash
python -m oss_policy_kit evaluate --target . --profile github-level-1 \
  --output-dir ./out --sarif-output evaluation-report.sarif --fail-on fail
```

Relative paths are resolved under `--output-dir`. Absolute paths are honored as-is.

Mapping highlights (full details in `docs/reports-contract-v1.0.md`):

- One SARIF result per `fail` or `manual-review-required` finding.
- `fail` → `level: error`, `manual-review-required` → `level: warning`.
- Repository-level findings emit `uri: "."` and **omit** `region` (no fake line ranges).
- File-backed findings emit `uri` relative to `%SRCROOT%`.
- `properties.security-severity` is derived from weight × status.
- `partialFingerprints.controlAndProfile/v1` enables stable deduplication across runs.

To upload SARIF to GitHub code scanning, use the standard `github/codeql-action/upload-sarif` action (or any consumer that accepts SARIF 2.1.0 logs).

## Evidence Model v2 — what changes for control authors

`reports/1.0` projects each result through `oss_policy_kit.application.evidence_projection` to produce a structured `evidence` block. Existing evaluators do **not** need to change: the projection reads `evidence_sources`, `evidence_collection_method`, `assurance`, `status`, and the `extra` mapping.

If you maintain external evaluator plugins, you can populate richer `extra` keys to improve trust projection:

| Key on `extra` | Effect |
|---|---|
| `collected_at` (ISO8601) | Drives `freshness_status`; without it, `freshness_status: unknown` for live evidence. |
| `attested_by` (string) | Promotes `attestation_status` from `self_attested` to `signed` when the source is `api_collected`. |
| `source_platform` | Used directly when present; otherwise inferred from the control id prefix. |
| `digest` (`sha256:...`) | Surfaced in the v1 `evidence.digest` field. |
| `evidence_schema_id` | Surfaced in the v1 `evidence.evidence_schema_id` field. |

These keys are read-only inputs to the projection. They are not required.

## Bundled schema hygiene

The bundled v3 schema (`src/oss_policy_kit/data/schema/evaluation-report-v3.schema.json`) was UTF-16 with BOM in v4. v5.0.0 re-encodes it as UTF-8 without BOM. Behavior is unchanged; downstream validators that previously failed on UTF-16 should now succeed.

## What did NOT change

- `--fail-on` semantics (`none | fail | degraded`). Same exit codes, same gate roles.
- Bundled control catalog and profile control IDs.
- Markdown report (`evaluation-report.md`) layout. Markdown still reads from the in-memory result fields and is not yet contract-versioned.
- `evaluate-many`, `recommend-profile`, `scaffold-evidence`, `collect-evidence`, `diff-reports` CLI surfaces.
- Python minimum version (`>=3.12`).
- Package classifier — remains `Development Status :: 4 - Beta`.

## Verifying the migration

After upgrading:

```bash
python -m oss_policy_kit --version          # expect 5.0.0+
python -m oss_policy_kit evaluate --target . --profile github-level-1 \
  --output-dir ./out
python -c "import json; d=json.load(open('out/evaluation-report.json'));
           print(d['schema_version'])"      # expect .../reports/1.0
```

If you see a `0.3`-shaped payload with `--report-json-contract 1.0`, the kit on `PATH` is still v4.x — recheck the venv and `python -m oss_policy_kit --version`.
