# Migration guide: v5.8.1 → v5.9.0

v5.9.0 is an **additive minor release** in the `5.x` line with **one description-only breaking change** to the `cra-eu-strict-1` profile (no functional / wire impact). The JSON wire contract `reports/1.0` is byte-stable; existing profile IDs and control IDs are unchanged. The new surfaces (controls, profile, subcommand) are additive.

The kit's `Development Status` classifier in `pyproject.toml` is promoted from `4 - Beta` to `5 - Production/Stable` — a signal of long-standing usability as a release gate, not a breaking change.

## TL;DR

| Change | Action required |
|---|---|
| Eleven new controls (`GOV-DISC-065` + 4 SARIF adapters + 6 `GL-PIPE-*`) | None unless you opt-in. |
| New `cra-eu-reporting-1` profile | None. Opt-in by passing `--profile cra-eu-reporting-1`. |
| New `gitlab-level-1` profile + GitLab CI parser | None. Opt-in if your project lives on GitLab CI; parser runs on every evaluate but produces empty analysis when no `.gitlab-ci.yml` exists. |
| New `emit-vex` subcommand (v0.2: per-CVE waivers, `--validate`, `--include-references`) | None. Run `oss-policy-kit emit-vex --help` to see the surface. |
| New `init --interactive` flag | None. Existing non-interactive flow unchanged. |
| `appsec-sast-sca-1` grew from 11 → 15 controls | Re-run `evaluate --profile appsec-sast-sca-1` against your repo to refresh the report. SAST adapters return `manual-review-required` until SARIF evidence is supplied. |
| `cra-eu-strict-1` description rewritten | None functionally. Update any dashboard that parses the profile description string. |
| Official `Dockerfile` + GHCR publish workflow | None until you tag and push. The publish workflow triggers on `v*` tags. |
| `pyproject.toml`: `Development Status :: 5 - Production/Stable` | None. Classifier signals long-standing release-gate usability. |
| `__version__` bumped to `5.9.0` | None. |

## What's new

### Eleven new controls

All `experimental` lifecycle so adopters can opt-in incrementally before they harden into `stable`.

- **`GOV-DISC-065` — Disclosure channel SLA documented (CRA reporting readiness).**
  Reads `.oss-policy-kit/evidence/disclosure-policy.json` (schema `disclosure-policy/v1`) with required fields `schema_version` (literal `"disclosure-policy/v1"`), `attested_at` (ISO date), `attested_by`, `contact.method/value`, `acknowledgement_sla_hours`, `triage_sla_hours`, `public_disclosure_policy.{default_window_days, negotiable}`. See `examples/hardened-repo/.oss-policy-kit/evidence/disclosure-policy.json` for a copy-paste-ready shape. Signal fallback: looks for SLA keywords in `SECURITY.md` (root, `.github/`, `docs/`). Category: governance.
- **`SAST-ZIZMOR-066` — zizmor SARIF findings (GitHub Actions AST analysis).**
  Reads `.oss-policy-kit/evidence/sast/zizmor.sarif.json`. Fails on `error`-level findings; warning / note are tolerated. Category: ci_cd.
- **`SAST-POUTINE-067` — poutine SARIF findings (GitHub Actions + GitLab CI).**
  Reads `.oss-policy-kit/evidence/sast/poutine.sarif.json`. Same severity policy as zizmor. Category: ci_cd.
- **`SAST-OSV-068` — OSV-Scanner v2 SARIF findings (reachability-aware SCA).**
  Reads `.oss-policy-kit/evidence/sast/osv-scanner.sarif.json`. Fails on `error`-level findings. Category: supply_chain. Pairs with the new `emit-vex` subcommand for CycloneDX VEX 1.6 emission.
- **`SAST-GITLEAKS-069` — Gitleaks SARIF findings (secret leak detection).**
  Reads `.oss-policy-kit/evidence/sast/gitleaks.sarif.json`. **Zero-tolerance** — any finding (even `warning`-level) blocks. Category: secure_development.

#### GitLab CI native controls (`GL-PIPE-001..006`)

The kit's first native GitLab CI support. Reads `.gitlab-ci.yml` at repo root or under `.gitlab/`. All `experimental`, category `ci_cd`. See ADR-003 for the full 12-control design; v5.9.0 ships the initial 6 most-impactful checks:

- **`GL-PIPE-001`** — pipeline files present and parseable (deterministic, weight 1).
- **`GL-PIPE-002`** — `image:` references pinned to a tag or digest (signal, weight 2).
- **`GL-PIPE-003`** — no `curl|sh` / `wget|sh` patterns in `script:` blocks (signal, weight 3).
- **`GL-PIPE-004`** — no broad `inherit: secrets: true` (deterministic, weight 2).
- **`GL-PIPE-005`** — `include:` does not reference unpinned remote URLs (signal, weight 2).
- **`GL-PIPE-006`** — jobs declare trigger restrictions (`rules:` / `only:` / `except:` / `when:`) (signal, weight 1).

Pair these with the existing `SAST-POUTINE-067` adapter (poutine SARIF) for deeper AST analysis.

### New bundled profile `gitlab-level-1`

Starter ladder for projects using GitLab CI/CD. Sixteen controls: governance core (6) + GitLab CI native (6) + dependency hygiene / release / SBOM (4). `--fail-on fail` recommended. Six of the controls (`GL-PIPE-*`) are experimental in this release; they harden to stable as the parser matures. `gitlab-level-2` and `gitlab-level-3` ladder profiles are planned for subsequent minors.

### New bundled profile `cra-eu-reporting-1`

Focused on the EU CRA's **2026-09-11** 24-hour reporting deadline. Eleven controls covering disclosure channel + SLA (`GOV-SEC-001`, `GOV-DISC-013`, **`GOV-DISC-065`**), detection capability (`SEC-DEPREV-011`, `DEP-UPDATE-001`, `SEC-SECRETS-050`), audit trail (`AUDIT-STREAM-060`, `GOV-EVIDFRESH-054`), risk handling (`GOV-WAIV-014`), and affected-artifact identification (`REL-CHANGE-012`, `BUILD-SBOM-QUAL-003`).

Advisory (`--fail-on degraded` recommended). Triggers the `[advisory profile]` banner. Excluded from `recommend-profile` suggestions (operator-choice only).

### New `emit-vex` subcommand (v0.2)

```bash
python -m oss_policy_kit emit-vex \
  --osv-sarif .oss-policy-kit/evidence/sast/osv-scanner.sarif.json \
  --waivers waivers/waivers.yaml \
  --validate \
  --include-references \
  --output vex.cyclonedx.json
```

Emits CycloneDX VEX 1.6 from OSV-Scanner SARIF. Findings without a matching waiver get `analysis.state: in_triage`; findings matched by a waiver carrying `vulnerability_ids: [...]` get `state: not_affected` with the waiver's justification text. See [`docs/vex-emission.md`](vex-emission.md).

### Waiver schema extension (additive)

`waivers/waivers.yaml` now accepts a per-vulnerability entry shape alongside the existing per-control shape:

```yaml
version: 1
waivers:
  # Existing per-control shape (unchanged):
  - control_id: CI-DANGER-007
    justification: "pull_request_target required; restricted to label-gated runs."
    owner: security@example.com
    status: approved
    expires_at: "2026-12-31"

  # New per-vulnerability shape (v5.9.0; consumed only by emit-vex):
  - vulnerability_ids:
      - CVE-2024-12345
      - GHSA-aaaa-bbbb-cccc
    justification: "Vulnerable function path unreachable; verified via static analysis."
    vex_justification: code_not_reachable  # optional CycloneDX VEX enum value
    owner: appsec@example.org
    status: approved
    expires_at: "2027-12-31"
```

The per-vulnerability shape is consumed **only** by `emit-vex`. The evaluation engine (which gates on profiles) ignores it. Existing per-control waivers continue to work unchanged.

### New evidence schema `disclosure-policy/v1`

`src/oss_policy_kit/data/schema/evidence-disclosure-policy.schema.json` (mirrored at `reports/schema/`). Required fields:

- `schema_version: "disclosure-policy/v1"`
- `attested_at` (ISO-8601 date), `attested_by`
- `contact.method` (email | url | form | pgp) + `contact.value`
- `acknowledgement_sla_hours` (integer ≥ 1)
- `triage_sla_hours` (integer ≥ 1)
- `public_disclosure_policy.default_window_days` (integer ≥ 0) + `public_disclosure_policy.negotiable` (boolean)

Optional fields: `safe_harbor`, `out_of_scope`, `cve_assignment_authority`, `collection`, `notes`. See `examples/hardened-repo/.oss-policy-kit/evidence/disclosure-policy.json` for a populated example.

### Pre-commit hook surface

New `.pre-commit-hooks.yaml` ships three hooks:

- `oss-policy-kit-evaluate` — for hard-gate ladders (`--fail-on fail`).
- `oss-policy-kit-evaluate-degraded` — for advisory profiles (`--fail-on degraded`).
- `oss-policy-kit-validate-profiles` — for kit maintainers / catalog extensions.

See [`docs/pre-commit-integration.md`](pre-commit-integration.md).

### `appsec-sast-sca-1` expanded (11 → 15 controls)

The AppSec native bundle adds the four new SARIF adapters. Existing `evaluate --profile appsec-sast-sca-1 --fail-on fail` runs continue to behave the same when the new SARIF evidence files are absent — the adapters return `manual-review-required`, which does NOT trip `--fail-on fail`. Adopters who supply the SARIFs gain the corresponding coverage.

If your pipeline already pins `appsec-sast-sca-1` and tracks the control count somewhere (a dashboard, a status check), update the expected count from 11 to 15.

## Breaking change

### `cra-eu-strict-1` description rewritten

**Functional impact: zero.** Same 19 controls, same `--fail-on degraded` recommendation, same CLI maturity label (`framework-aligned advisory (regulatory)`).

**Description-string impact: yes.** The profile previously self-described as:

> "Hard-gate-capable when evidence files are filled. Without evidence, results in manual-review-required (honest gap, not a crash)."

It now reads:

> "Regulatory mapping (advisory only). Do not use as a release gate. Not a compliance certification. [...] **Posture:** advisory."

Rationale: the kit does not certify CRA conformity (which requires a competent authority / notified body), and "hard-gate-capable" overpromised what evidence-backed evaluation alone can demonstrate. The new wording matches the CLI maturity label and `cra-eu-ready-1`'s phrasing for consistency.

**Action required**: if your CI dashboard, evidence pipeline, or release-readiness page parses the profile description string and matches on "hard-gate-capable", update the matcher. The profile id, control list, and `reports/1.0` JSON shape are unchanged.

The test carve-out that previously allowed `cra-*` profiles to surface either "advisory" or "hard-gate-capable" in their description was removed; all advisory profiles (including the regulatory ones) must now surface "advisory" or an equivalent disposition phrase.

## Deferred to v5.9.x / v5.10 (additive, planned)

Tracked in [`docs/profiles/deferred-followups.md`](profiles/deferred-followups.md):

- `emit-vex` extensions: full CycloneDX 1.6 JSON Schema validation (today `--validate` is structural / required-field only), `response.type` mapping from waiver fields, multi-source ingest for zizmor / poutine / Gitleaks SARIF.
- Remaining GitLab CI controls `GL-PIPE-007..012` (OIDC tokens, self-hosted-runner restrictions, audit-log streaming) plus the `gitlab-level-2` / `gitlab-level-3` ladder profiles. See ADR-003.
- Container image roadmap: digest-pinned base image, `--source-date-epoch` for byte-reproducible images.
- GitHub 2026 native security platform features (egress firewall, scoped secrets, workflow dependency locking) — GA-dependent.

```bash
  --target ./examples/hardened-repo \

  --summary-only
```
