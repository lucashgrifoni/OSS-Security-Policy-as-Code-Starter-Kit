# v9.0.0 migration guide

v9.0.0 is a **breaking** major. Two changes affect adopters; both are advisory-friendly and most users are unaffected.

## 1. Legacy report contracts removed — `reports/2.0` is the only contract (ADR-043)

`reports/2.0` has been the **default** report contract since v7.0.0. The legacy pre-2.0 contracts
(`reports/0.1`, `reports/0.2`, `reports/0.3`, `reports/1.0`) were kept selectable through one
deprecation cycle and are **removed in v9.0.0**.

**What changed**
- `--report-json-contract` now accepts **only** `2.0` (or empty, which means `2.0`). Passing
  `1.0`/`0.3`/`0.2`/`0.1` is a clean usage error (exit `2`) that names the removed contract and points
  here — never a silent fallback.
- The `oss-policy-kit.yaml` `report_json_contract:` config key follows the same rule.
- The JSON report's `gate_execution_model` / `summary_by_gate_role` fields (a `reports/0.3`/`1.0`
  extension) are gone; `reports/2.0` does not carry them.

**Who is affected:** only adopters who explicitly pinned a legacy contract
(`--report-json-contract 1.0` / `0.3` / `0.2`, or the equivalent config/CI value). Default users are
unaffected — `reports/2.0` has been the default for two majors.

**How to migrate**
1. Remove any `--report-json-contract` flag pinned to `1.0`/`0.3`/`0.2`, or set it to `2.0`. The same
   for `report_json_contract:` in `oss-policy-kit.yaml` and the GitHub Action input.
2. Update any consumer that parses the report JSON to the `reports/2.0` shape:
   - controls are under **`controls`** (was `results`), each keyed by **`id`** (was `control_id`) with a
     **`state`** field (was `status`: `PASS`/`FAIL`/`UNKNOWN`/`NOT_APPLICABLE`/`ATTESTED`/`SELF_ATTESTED`)
     and a **`message`** field (was `reason`);
   - profile metadata is under **`profile`** (`profile.id`, `profile.title`, …) instead of the flat
     `profile_id` / `profile_title`.
   See [docs/reports-contract-v2.0.md](reports-contract-v2.0.md) for the full shape.
3. If you still have **old `reports/1.0` report files** to convert, `scripts/migrate-1.0-to-2.0.py`
   reshaped a stored 1.0 report into 2.0. That script was **removed in v10.0.0** — see
   [§3 of the v10.0.0 migration guide](v10.0.0-migration-guide.md#3-scriptsmigrate-10-to-20py-is-removed)
   for how to recover it from `v9.0.3`.

## 2. CRA profile tightened + renamed (ADR-029)

The canonical CRA profile was tightened from "readiness" to **conformance-evidence** and renamed
`cra-eu-ready-2-1` → `cra-eu-conformance-evidence-1`.

- The old id `cra-eu-ready-2-1` still resolves as a **deprecated alias** (with a stderr warning) through
  the v9.x line and is removed in v10.0.0 — update your `--profile` / config references to
  `cra-eu-conformance-evidence-1`.
- The profile now requires additional obligation-evidence controls (published VDP / `security.txt`,
  SBOM, document retention, incident-reporting readiness, artifact-integrity verification), so a
  repository that passed the old readiness bundle may resolve to `manual-review-required` for the new
  controls until the corresponding evidence is present. Recommended `--fail-on degraded` for this
  advisory profile. It maps evidence to CRA obligations and **never** claims certification.
