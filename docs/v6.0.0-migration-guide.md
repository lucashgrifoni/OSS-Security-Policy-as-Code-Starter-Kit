# v6.0.0 migration guide

> **In development (v6.0.0)**. This page consolidates the migration steps for the three breaking changes planned for v6.0.0. **Nothing here is final until v6.0.0 GA ships.** Migration steps may be refined as PRs land on `feat/v6.0.0-evolution`.

This guide is the single migration source for v6.0.0. It covers the three documented breaking changes plus one assurance-mix shift that may affect adopters parsing the JSON shape.

## Breaking-change summary

| ID | Change | Source ADR | Adopter impact | Migration effort |
|---|---|---|---|---|
| **M-003** | `recommend-profile/v2.schema_version` becomes an absolute URL | ADR-008 | String-match consumers break | Trivial |
| **B-001** | `reports/2.0` becomes the default report contract | ADR-013 | Dashboard consumers re-map statuses | Low to moderate (depends on dashboard count) |
| **B-002** | `--format chainloop` of `export-evidence` is experimental | ADR-012 | Output may shift inside v6.0.x | Pin kit version; watch CHANGELOG |
| **A-001** | `GH-PROV-023` `assurance_mix` shift (signal → evidence-backed) | ADR-007 | Adopters parsing `assurance_mix` of release-hardening profiles see new mix | Low |

## M-003 — `recommend-profile/v2.schema_version` URL

### Before (v5.9.x)

```json
{
  "schema_version": "oss-policy-kit/profile-recommendation/v2",
  "signals_detected": [...],
  "suggestions": [...]
}
```

### After (v6.0.0)

```json
{
  "schema_version": "https://schemas.lucashgrifoni.io/oss-policy-kit/recommend-profile/v2.json",
  "signals_detected": [...],
  "suggestions": [...]
}
```

### What you need to do

- **String-match consumers**: replace the exact-match check with one of:
  - `endswith("/recommend-profile/v2.json")`
  - `schema_version in {OLD_VALUE, NEW_VALUE}` for a one-minor transition
- **Schema-fetching consumers**: the new URL is resolvable; you can fetch the schema directly.
- **Structure-only consumers** (parse by shape): no change.

### Backward compatibility

The kit's own internal consumers (`diff-reports`, snapshot tests) accept **both** values during v6.0.x. The backward-compat parsing is removed in v6.1.0.

## B-001 — `reports/2.0` default

The full details are in [`reports-contract-v2.0.md`](reports-contract-v2.0.md). Summary of migration steps:

1. **Identify your dashboards** that consume `evaluation-report.json`.
2. **Pick a transition window** within the v6.0.x line. `reports/1.0` remains selectable via `--report-json-contract=1.0`; choose whether to migrate dashboards before or after upgrading CI to v6.0.0.
3. **For each dashboard**:
   - Update the contract-version check to accept `reports/2.0` (`"contract_version": "reports/2.0"`).
   - Re-map status switches per the table in [`reports-contract-v2.0.md`](reports-contract-v2.0.md#mapping-from-reports10-to-reports20).
   - Most common gotcha: `degraded` is now `FAIL` with a `degraded: true` per-control flag.
   - For consumers branching on `manual-review-required` / `skipped` / `error`: those three converge under `UNKNOWN` with distinct `reason` sub-field values.
4. **Optional**: opt into `ATTESTED` highlighting for stronger release-gate evidence presentation.
5. **Pin to `--report-json-contract=1.0`** during the migration if you cannot finish dashboard migration before upgrading. A deprecation warning prints on stderr; it does not fail the gate.

### Migration script

```text
$ python scripts/migrate-1.0-to-2.0.py \
    --input out/old/evaluation-report.json \
    --output out/new/evaluation-report.json
```

Convert offline-captured `reports/1.0` outputs to `reports/2.0` for dashboards that backfill historical data.

### Deprecation timeline

- **v6.0.0 GA**: `reports/1.0` selectable, deprecation warning on stderr.
- **v6.0.x patches**: same as v6.0.0 GA.
- **v6.1.0**: `--report-json-contract=1.0` becomes a usage error.

## B-002 — `export-evidence --format chainloop` is experimental

The full details are in [`evidence-export.md`](evidence-export.md) and ADR-012.

The Chainloop ingest spec is pre-1.0. The contract from the kit:

- The **subcommand surface** is stable.
- The **output shape for `--format chainloop`** may change inside v6.0.x.
- **Promotion to stable** happens in v6.1.0 based on Chainloop spec stability.

### What you need to do

- **Pin the kit version** if you wire `export-evidence --format chainloop` into production CI.
- **Watch the CHANGELOG** `## Unreleased` section for entries mentioning `export-evidence` or Chainloop.
- **Open an issue** on the kit repo if the Chainloop ingest spec moves before the kit catches up.

`--format sarif` is stable; safe to wire into CI without pinning.

## A-001 — `GH-PROV-023` `assurance_mix` shift

The full details are in ADR-007.

`GH-PROV-023` was `signal`-grade in v5.x; v6.0.0 promotes it to `evidence-backed`. The profile-level `assurance_mix` for any profile bundling `GH-PROV-023` shifts accordingly. Profiles affected:

- `github-release-hardening-1`
- `github-release-hardening-2`
- `github-release-hardening-3`
- `slsa-build-l2-1`

### What you need to do

- **If you parse `assurance_mix`** of any of the four profiles in dashboards or reports: expect the `evidence-backed` count to be one higher and the `signal` count to be one lower than in v5.9.x output for the same profile.
- **If you do not have a per-artifact provenance evidence file** with the `verification:` block populated, `GH-PROV-023` will return `manual-review-required` (`UNKNOWN reason: manual-review-required` in `reports/2.0`). The gate does **not** regress — you keep the v5.x non-blocking behavior until you add evidence.
- **To populate the evidence file**: after a release, run `gh attestation verify <artifact> --format json` (or `cosign verify-bundle <artifact>`) and persist the relevant fields into `.oss-policy-kit/evidence/github-provenance-artifact.json` under the `verification:` block. The schema is `src/oss_policy_kit/data/schema/evidence-github-provenance-artifact.schema.json`.

## Upgrade checklist

In order:

1. **Read this guide and the four ADRs referenced** (007, 008, 012, 013).
2. **Pin the previous version in CI** (`oss-policy-kit==5.9.1`) before starting the upgrade.
3. **Upgrade in a non-blocking environment first** (a staging CI, a fork, or a local clone) and run your test suite against `oss-policy-kit==6.0.0`.
4. **Migrate dashboards** that parse `evaluation-report.json` or `recommend-profile` output. The mapping tables above are the source of truth.
5. **Populate the `verification:` block** for any release-hardening adopter who wants to keep the `evidence-backed` posture on `GH-PROV-023`.
6. **Promote v6.0.0 to production CI** once dashboards and evidence files are updated.
7. **Plan removal of `--report-json-contract=1.0`** before v6.1.0 lands.
