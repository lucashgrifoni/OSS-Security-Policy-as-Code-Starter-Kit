# v4.0.0 Migration Guide

This guide covers breaking changes and maturity goals **targeted for** **v4.0.0**. The major is **not yet tagged or published**; this document describes what adopters should expect **once** **`v4.0.0`** ships, and what the current development branch implements in preparation.

The v4.0.0 release is not a "rename-only" major. It combines:

1. mandatory cleanup of deprecated controls carried through the v3.x line
2. at least two maturity fronts that make the major defensible in product and release notes

Maturity fronts **planned for** this line (implementation tracks the checklist in **`CHANGELOG.md`**):

- report contract and gate semantics (`reports/0.3`)
- profile ergonomics and live-only posture modeling (CLI discovery flags + JSON metadata)
- release and supply-chain hardening (pinned GitHub Actions in the publish workflow)

---

## Confirmed Breaking Changes

### SEC-AUDIT-016 - Dependency vulnerability scan (pip-audit or SCA) in CI

**Removal reason:** Static keyword inspection of workflow YAML cannot prove that a dependency scan executed on real dependency graphs, enforced thresholds, or produced actionable results.

**Behavior in v3.x (final):** Evaluator returned `NOT_EVALUATED` with migration guidance.

**Target v4.0.0 behavior:** The control is removed from the catalog, from bundled profiles, and from supported evaluator paths. Custom profiles that still reference it **fail at load time** with a migration-oriented error once adopters move to **v4.0.0**.

**Recommended replacements:**

| Coverage area | Replacement control |
|---|---|
| SAST / security scanning in CI | `SEC-CODEQL-010` |
| Secret detection | `SEC-SECRETS-050` |
| Dependency quality assurance | `BUILD-SBOM-QUAL-003` |
| Supply-chain SCA posture | `SEC-DEPREV-011` |

**Migration action:** Replace `SEC-AUDIT-016` in custom profiles before adopting v4.0.0.

---

### CI-SBOM-017 - SBOM generation in release or package workflow

**Removal reason:** Keyword detection in workflow YAML does not validate SBOM format, completeness, signing, or linkage to released artifacts.

**Behavior in v3.x (final):** Evaluator returned `NOT_EVALUATED` with migration guidance.

**Target v4.0.0 behavior:** The control is removed from the catalog, from bundled profiles, and from supported evaluator paths. Custom profiles that still reference it **fail at load time** with a migration-oriented error once adopters move to **v4.0.0**.

**Recommended replacements:**

| Platform | Replacement control |
|---|---|
| Any platform | `BUILD-SBOM-QUAL-003` |
| GitHub Actions | `GH-PROV-023` |
| AWS CodeBuild / CodePipeline | `AWS-SBOMART-058` |
| AWS provenance | `AWS-PROVART-059` |
| Azure Pipelines | `AZ-ARTSBOM-058` |
| Azure provenance | `AZ-ARTPRV-059` |

**Migration action:** Replace `CI-SBOM-017` in custom profiles before adopting v4.0.0.

## Custom Profile Migration

If you maintain a custom profile YAML, treat this as the minimum migration:

```yaml
# Before (valid in v3.x, invalid in v4.0.0)
controls:
  - SEC-AUDIT-016
  - CI-SBOM-017

# After (v4.0.0-compatible example)
controls:
  - SEC-CODEQL-010
  - SEC-SECRETS-050
  - BUILD-SBOM-QUAL-003
  - GH-PROV-023  # or AWS-SBOMART-058 / AZ-ARTSBOM-058 depending on platform
```

Expected loader behavior in v4.0.0:

- bundled profiles must not reference removed controls
- custom profiles referencing removed controls must fail load with a clear migration-oriented error
- docs and examples must show the replacement path, not the deprecated IDs

## Approved Maturity Fronts For v4.0.0

The major should ship with at least two of the following three fronts.

### 1. Report contract and gate semantics

Why this belongs in a major:

- `reports/0.2` already carries assurance and evidence-collection concepts
- deferred follow-ups explicitly call out a new JSON schema version and richer gate semantics as future scope
- this is the right place to clarify what is a hard gate, what is advisory, and what is only evidence context

Recommended direction:

- introduce a new report contract version instead of mutating `reports/0.2` in place
- prefer explicit gate-role modeling over a misleading single score
- keep trust boundaries visible: clone-visible, evidence-backed, live-only, and manual-review cases must remain distinguishable

Minimum success criteria:

- new contract version documented and tested
- CLI gate behavior aligned with the new summary semantics
- migration notes for downstream JSON consumers

### 2. Profile ergonomics and live-only posture modeling

Why this belongs in a major:

- deferred follow-ups already identify profile flags, new catalog/profile fields, and live-only posture modeling as scope expansion
- current docs are honest about platform limits, but product surface can make those limits easier to consume programmatically

Recommended direction:

- add profile-discovery ergonomics such as `--family`, `--only-extreme`, and `--advisory-only`
- model live-only posture explicitly in product metadata instead of leaving it only in prose
- keep `github-aws-level-2` and `github-azure-level-2` advisory until collector and evidence maturity justifies anything stricter

Minimum success criteria:

- human and JSON surfaces expose the new profile/live-only distinctions clearly
- no bundled profile is silently reclassified into a hard gate without migration notes
- docs and examples explain how to choose between starter, advisory, extreme, and live-evidence-heavy paths

### 3. Release and supply-chain hardening

Why this belongs in a major:

- the project now treats PyPI, GitHub Releases, SBOM, and TestPyPI as active distribution concerns
- release-readiness guidance already requires pinned actions and reproducible validation, but the publish workflow still needs alignment

Recommended direction:

- pin third-party GitHub Actions in publish workflows to full commit SHAs
- keep TestPyPI-first publication discipline as a hard release rule
- publish SBOM consistently and, where feasible, add provenance or attestation for release artifacts
- keep GitHub Release creation and package publication reproducible, not manual-only

Minimum success criteria:

- publish workflow pinned and validated
- TestPyPI and PyPI paths documented as a reproducible sequence
- release notes, SBOM handling, and distribution assets aligned with the release checklist

## Guardrails

The following are explicitly out of scope unless separately approved:

- inventing unsupported evidence JSON fields just to produce more PASS results
- converting advisory hybrid profiles into hard gates without stronger evidence semantics
- introducing a numeric security score that hides assurance or trust-boundary differences
- removing a legacy alias or changing bundled control lists without migration notes and tests

---

## Release Exit Criteria

Do not tag `v4.0.0` until all of these are true:

- `SEC-AUDIT-016` and `CI-SBOM-017` are removed from the catalog, evaluator paths, bundled profiles, examples, docs, and templates
- migration tests prove bundled-profile safety, clear failure for custom profiles, and documented replacements
- at least two approved maturity fronts are fully implemented
- release docs, migration guide, README, and examples no longer describe the major as "future cleanup"
- packaging, TestPyPI, PyPI, GitHub Release, and SBOM paths are reproducible from maintainer docs

---

## Suggested Rollout Shape

Use a staged path:

1. lock the v4.0.0 scope and guardrails in docs
2. land the mandatory deprecated-control cleanup first
3. implement the selected maturity fronts with tests and docs
4. run a release-candidate cycle on TestPyPI
5. tag `v4.0.0` only after the migration and release evidence are green
